# neon-uci

`neon-uci` is NeonWrt's UCI → systemd translation layer.

It does **not** replace UCI, ubus, rpcd, LuCI, or netifd. The intended split is:

```text
LuCI / rpcd
    |
   UCI
    |
    +---------------------> netifd ---------> Linux networking
    |
    +----> neon-uci -----> systemd-native / generic daemon configuration
```

## Why this exists

OpenWrt packages often rely on `/etc/init.d/*` glue to turn UCI configuration into daemon command lines or generated configuration files. In NeonWrt, systemd owns service lifecycle, so this glue needs a systemd-native home without forcing every package to embed one-off logic into its unit file.

`neon-uci` supplies that layer.

## Runtime design

1. `neon-uci.service` performs an initial translation pass.
2. The daemon watches `/etc/config` with inotify.
3. UCI commits normally replace/write the affected package file.
4. Changes are debounced for 250 ms.
5. Only translators that declare the changed UCI package are executed.
6. A translator writes configuration atomically.
7. Only after a successful translation does the core request the configured systemd reload/restart action.

Uncommitted UCI deltas are intentionally ignored. `uci commit` is the apply boundary.

## Installed translators

### hostname

Input:

```text
/etc/config/system
system.@system[0].hostname
```

Output:

```text
/etc/hostname
running kernel hostname
```

### systemd-timesyncd

Input:

```text
/etc/config/system
system.ntp.enabled
system.ntp.server
```

Anonymous `@timeserver[0]` is accepted as a fallback.

Output:

```text
/run/systemd/timesyncd.conf.d/50-neon-uci.conf
```

### systemd-journald

Input:

```text
/etc/config/neon_systemd
```

Output:

```text
/run/systemd/journald.conf.d/50-neon-uci.conf
```

The `/run` location is intentional: UCI remains the source of truth and the generated files disappear at boot, then are recreated by `neon-uci`.

## Why there is no network translator

When NeonWrt keeps netifd, `/etc/config/network` already has a mature consumer:

```text
/etc/config/network -> libuci -> netifd -> netlink -> kernel
```

Do not create a networkd translator for the same interfaces unless you explicitly remove netifd ownership. Running netifd and systemd-networkd against the same interfaces creates two network state managers.

## Manifest format

Files under `/etc/neon-uci.d/*.conf` are processed in lexical order.

```ini
[translator]
name=example
packages=foo,bar
command=/usr/libexec/neon-uci/translate-example
units=example.service
action=try-reload-or-restart
unit_optional=yes
enabled=yes
```

Fields:

- `name`: translator identifier.
- `packages`: comma-separated UCI package names that trigger it.
- `command`: absolute path to the translator executable. It receives `apply` as argv[1].
- `units`: comma-separated systemd units affected by generated configuration.
- `action`: `none`, `reload`, `restart`, `try-reload-or-restart`, `reload-or-restart`, or `daemon-reload`.
- `unit_optional`: if `yes`, a missing unit is skipped instead of failing the translation.
- `enabled`: enables/disables this translator.

The handler also receives `NEON_UCI_CHANGED_PACKAGES` in its environment.

## Adding a translator

Create `/usr/libexec/neon-uci/translate-example`:

```sh
#!/bin/sh
set -eu
. /usr/libexec/neon-uci/common.sh
[ "${1:-}" = apply ] || exit 2

value="$(uci_get 'example.main.value' 'default')"
{
    echo '# Generated by neon-uci. Do not edit.'
    printf 'Value=%s\n' "$value"
} | atomic_write /run/example/generated.conf 0644
```

Then create `/etc/neon-uci.d/40-example.conf`:

```ini
[translator]
name=example
packages=example
command=/usr/libexec/neon-uci/translate-example
units=example.service
action=try-reload-or-restart
unit_optional=no
enabled=yes
```

Check it:

```sh
neon-uci --check
neon-uci --apply example
```

A later normal UCI commit is automatic:

```sh
uci set example.main.value='new-value'
uci commit example
```

## CLI

```text
neon-uci                         run daemon
neon-uci --once                  apply all translators once
neon-uci --apply system          apply translators depending on system
neon-uci --check                 validate translator manifests
neon-uci get system.@system[0].hostname
neon-uci list system.ntp.server ' '
systemctl reload neon-uci        force a full retranslation via SIGHUP
```

## Interaction with neon-procd

The two components solve different compatibility problems:

```text
neon-procd : OpenWrt/procd service lifecycle -> systemd
neon-uci   : UCI configuration semantics      -> systemd-native config
```

OpenWrt-native components that already consume UCI directly should keep doing so. In particular, netifd should not be routed through `neon-uci` merely for consistency.

## Recommended boot stack

```text
systemd
  +-- ubusd.service
  +-- netifd.service
  +-- rpcd.service
  +-- neon-uci.service
  +-- systemd-journald.service
  +-- systemd-timesyncd.service (optional)
```

`neon-uci` has no dependency on procd. It can coexist with `neon-procd` compatibility wrappers.

## NeonWrt hostname handling

`translate-hostname` writes `/etc/hostname` and then calls `neon-uci set-hostname NAME`.
The latter uses the Linux `sethostname(2)` system call directly, so minimal NeonWrt
images do not need the BusyBox `hostname` applet, D-Bus, `hostnamectl`, or
`systemd-hostnamed` merely to apply a UCI hostname change.
