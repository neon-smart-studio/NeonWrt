NeonWrt systemd PID 1 conversion
================================

Current base-files policy
-------------------------

* base-files depends on systemd and uci.
* /sbin/init is owned exclusively by the systemd package; base-files removes
  any stale /sbin/init from its own package image.
* preinit hands off through /sbin/init.  It does not hard-code the systemd
  binary path.
* /run and /run/lock exist in the on-disk image before PID 1 starts; systemd
  mounts/manages the runtime hierarchy during early boot.
* By default NeonWrt keeps the OpenWrt-compatible volatile /var -> /tmp
  layout.  CONFIG_TARGET_ROOTFS_PERSIST_VAR=y selects a persistent /var with
  /var/run -> /run and /var/lock -> /run/lock.
* systemd-tmpfiles creates the runtime directories expected by OpenWrt
  compatibility services.
* neon-root-rw.service remounts writable non-squashfs root filesystems rw
  before services need to update persistent configuration.

PID 1 ownership
---------------

Do not modify files/lib/preinit/99_10_run_init to start systemd.  Starting
systemd from a child preinit process does not make it PID 1.  systemd must be
started by the kernel through /sbin/init (or temporarily via init= on the
kernel command line).

The standard procd package and neon-procd compatibility package MUST NOT own
/sbin/init.  neon-procd runs as a normal service under systemd.

After the complete rootfs/image is assembled, verify:

  readlink staging_dir/target-aarch64_cortex-a72_glibc/root-bcm27xx/sbin/init

Expected target:

  /usr/lib/systemd/systemd

Locate packages which still try to create init with:

  grep -R "sbin/init" -n package feeds 2>/dev/null

If the flashed image still prints the traditional procd PID-1 startup path,
append this temporarily to the kernel command line:

  init=/usr/lib/systemd/systemd

If systemd then becomes PID 1, the remaining problem is final-rootfs init
ownership rather than the systemd executable itself.

UCI configuration generation under systemd
===========================================

Traditional OpenWrt creates the initial /etc/config/network and
/etc/config/system from a preinit hook.  NeonWrt cannot rely on that hook when
systemd is PID 1, so base-files installs and enables:

  neon-config-generate.service

It runs during sysinit after writable/local filesystem preparation and before
netifd, neon-uci and network-pre.target.  The helper:

* creates /etc/board.json with /bin/board_detect when it is missing;
* runs /bin/config_generate on every boot; config_generate only fills missing
  network/system packages and therefore preserves existing UCI configuration;
* guarantees a minimal /etc/config/system as a defensive fallback;
* initializes /etc/hostname and /proc/sys/kernel/hostname directly from UCI,
  without requiring hostname(1), hostnamectl, D-Bus or systemd-hostnamed.

The legacy files/lib/preinit/82_config_generate path remains supported.  It now
always invokes /bin/config_generate even when /etc/board.json already exists,
fixing the old case where an image containing board.json but no
/etc/config/system skipped system configuration generation entirely.

Generated default identity
--------------------------

The default generated system hostname is "NeonWrt" rather than "OpenWrt".
Board-specific JSON may still override the hostname, timezone, NTP servers and
other generated values.

Boot ordering hardening
----------------------
neon-config-generate.service is pulled in by sysinit.target and is also an
explicit dependency of neon-uci.service and neon-openwrt-rc.service through
base-files-installed drop-ins.  This prevents the UCI bootstrap from occurring
after neon-uci or the legacy OpenWrt rc bridge has already started.

Wi-Fi AP v4 timing fix
----------------------
- /usr/libexec/neon-wifi-config performs first-boot UCI generation only.
- It adds board.json.wlan={} when missing for wifi-detect compatibility.
- It retries wifi config until nl80211 returns a real PHY and wireless.radio* is generated.
- netifd + wpad/hostapd still own all Wi-Fi runtime state.
- 60/61 Wi-Fi UCI defaults return failure when a PHY exists but wireless UCI is not ready,
  preventing uci_apply_defaults from deleting them prematurely.
